# 智能粘贴缩进修复记录

## 目标

整块代码按目标位置统一平移，保留内部相对缩进。例如源代码的 class 为 0 格、字段为 4 格，粘到 12 格的位置后，应分别为 12 格和 16 格。不能仅对齐第一行，也不能让所有行缩进相同。

## 复现及原因（2026-10-05）

配置文件为 `lua/plugins/smart-paste.lua`。之前处理了 Ctrl-V 和剪贴板快捷键，但终端/GUI 的粘贴通过 `nvim_paste()` 调用 `vim.paste()`，不经过这些映射。

在完整 Neovim 配置中，创建 Python 缓冲区，在带 12 格缩进的空行进入插入模式，通过 `nvim_paste()` 粘贴 class 和三个带 4 格缩进的字段，修复前得到：第一行 12 格，字段仍为 4 格。该结果与用户截图一致。此前伪造剪贴板并触发 Ctrl-V 的测试未覆盖此入口，不能证明终端粘贴正常。

这证明终端入口存在该问题；没有直接连接用户已经打开的编辑器，因此不能断言截图中的操作一定走了此入口。

## 修改

保留原生 `vim.paste` 处理器，在其前面增加整块缩进转换：

- 插入模式和普通模式在行首空白区域粘贴多行文本时，以目标空白的显示宽度为基准。
- 源文本用非空行的最小缩进为基准，各行加上相同的缩进差，保留内部层级。
- 第一行扣除目标已有前缀的缩进，避免原生插入时重复添加。
- 分段传入的粘贴先拼接完整，再统一转换；相邻分段的边界可能位于同一行中间，不能擅自加换行。
- 单行文本、命令行及终端缓冲区保留原生处理。
- 根据目标 expandtab 设置使用空格或 tab；比较缩进应比较显示宽度，不应仅比较字节数。

## 验证

使用完整配置启动 headless Neovim，调用真实 `nvim_paste()`，没有替换剪贴板函数：

1. Python 源 class 为 0 格，字段为 4 格，目标 12 格：结果 12/16/16/16 格，通过。
2. 同样内容分三段发送，分段切在 Transaction 和 amount 单词中间：结果相同，通过。
3. 既有 Ctrl-V 普通、插入、行式可视及字符式可视替换回归测试通过。

脚本运行于 `/tmp/paste-real.lua` 与 `/tmp/full-nvim-smart-paste.lua`，这些临时脚本不是部署配置。

## 部署与后续排查

编辑此仓库的 `lua/plugins/smart-paste.lua` 后重启 Neovim：

```sh
nvim
```

已运行的 Neovim 不会自动重新执行插件 config，重新启动后加载更新。不要反复执行 config：会重复包装 vim.paste。

后续区分三条路径：终端粘贴（vim.paste）、Ctrl-V 映射、p/P 寄存器粘贴。上游 p/P 对字符式寄存器仍有原生路径，本次终端入口测试不能代替其测试。Visual、Replace 和代码行中间的终端粘贴仍交给原生处理，不能宣称所有模式均已智能对齐。

## COBOL 字符式复制补充修复

用户随后提供 READ / AT END / END-READ 的截图。新复现发现源第一行是 `READ INPUT-FILE`（0 格），后续行仍带源文件的 15/19/11 格缩进。目标为 15 格时，旧逻辑错误地产生 15/30/34/.../26 格。

字符式选择从首行第一个字母开始时，剪贴板没有该行前面的空白，不能简单地把零当作源缩进。

修复先恢复缺失的首行前缀，再统一移动：同一编辑器的字符式 yank 通过 TextYankPost 记录原始前缀，仅在粘贴内容与记录完全一致时使用。外部 COBOL 文本若以无缩进的语句开头且包含匹配的 END-语句，以结束语句的缩进恢复开始语句基准。没有原始信息且没有配对结束语句的外部文本仍可能存在歧义，不对所有片段承诺自动推断。

真实 nvim_paste 测试中，READ/END-READ 为 15 格，AT END/NOT AT END 为 19 格，内部语句为 23 格，全部通过。另用真实字符式 yank 后再终端粘贴验证 Python 内部层级恢复；完整/分段 Python 粘贴及既有 Ctrl-V 回归也通过。字符式复制包含末尾换行时保留该换行。
